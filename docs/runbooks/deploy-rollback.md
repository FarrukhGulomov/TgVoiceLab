# Deploy and roll back

**Deploy** (single Linux host, Docker Compose in `deploy/`):

0. One-time, as root: `sudo deploy/prepare-secrets.sh` creates the missing secrets with the owners the containers need (it never overwrites): the three database passwords owned by uid 999 (postgres), the data keys, admin token and Telegram session owned by uid 10001 (the image user), all mode 0400. File-based Compose secrets are bind mounts, so the container sees the host owner and mode; the app refuses group/world-readable secret files. Put the real Telegram session at `.local/secrets/telegram.session` (`pnpm spike:login`).
   Then create two env files (mode 600, never committed): `.env.production` with `DATABASE_URL=postgres://tgvl_app:<db_app_password>@db:5432/tgvl`, `OWNER_TELEGRAM_USER_ID`, `OWNER_TIMEZONE`, `MESSAGING_ADAPTER=telegram`, `TELEGRAM_API_ID/HASH`; and `.env.migrate` with only `DATABASE_URL=postgres://tgvl_migrator:<db_migrator_password>@db:5432/tgvl`.
   **Three database logins, never the same:** `tgvl_admin` (bootstrap superuser: initialises roles and break-glass maintenance only; the app never receives it), `tgvl_migrator` (owns the schema, applies forward-only migrations), `tgvl_app` (runtime: DML only; cannot run DDL, touch triggers, grant, or UPDATE/DELETE `audit_events`/`consent_events`; audit purge is a narrow function that refuses rows younger than 60 days). In production the process refuses to start if its login is a superuser, owns schema objects, can create objects, or can rewrite history (`DB_ALLOW_PRIVILEGED_ROLE=true` overrides, for non-production only). Roles are created from `deploy/postgres/roles.sql` on the first start of an empty data directory.
1. CI green on the commit (`pnpm verify` and the `deploy-smoke` job), image built with `--build-arg BUILD_FINGERPRINT=$(node scripts/build-fingerprint.mjs)`.
2. Back up the database ([restore.md](restore.md)). Apply migrations as the migrator: `docker compose -f deploy/docker-compose.yml run --rm migrate` (additive/forward-only; a modified applied file is refused by checksum; this step needs no application secrets).
3. Start with calls **off**: `docker compose -f deploy/docker-compose.yml up -d`. Check `curl -s localhost:8080/health/live`, then `/v1/capabilities` (authenticated).
4. Rolling update: the container gets SIGTERM, stops claiming work, asks every live call to end, lets the supervisors persist their state, closes the server and DB (hard cap 30 s). Never run two gateways on one Telegram session.

**Deployment smoke** (`deploy/smoke.sh`, also run in CI): builds the image and starts a disposable stack with temporary secrets, then asserts: roles initialise (app is not superuser, the migrator owns the schema); migrations apply as the migrator; the runtime login cannot create tables, delete audit history, or purge young audit rows; the assistant runs as uid 10001 with a read-only root filesystem and readable secrets; `/health/live` answers and `/health/ready` needs the token and reports the database; an over-privileged `DATABASE_URL` is refused. It does **not** touch Telegram or real data. Restricted networks can pass extra flags via `SMOKE_DOCKER_BUILD_ARGS`.

**Roll back:** deploy the previous image with calls disabled and the kill switch on until health is confirmed. Schema is expand/contract: do not roll the schema back
destructively; the previous image must tolerate newer additive columns (all migrations to date are additive). If a migration itself is bad, restore from backup.

**Verified vs not:** the image now runs as real containers in `deploy/smoke.sh` (database roles, migrations, least privilege, secrets, readiness). **Not verified:** a real host canary with Telegram (egress, session persistence, UDP/relay for calls) — gate G0-F.
